1. Introduction
1.1 Purpose
This document specifies the software requirements for the Online Complaint
Management System (OCMS), a Python web application that lets users file complaints
online, track them to resolution, and lets administrators and staff handle them from one
dashboard. It is the reference for design, coding, testing and evaluation of the project.
1.2 Scope
OCMS replaces paper forms, phone calls, emails and manual registers with a single
database-backed system. It covers user registration and login, complaint submission with
attachments, categorisation, assignment to staff, status tracking, admin responses,
feedback and reporting. It does not cover payment handling, native mobile apps or
integration with external ERP systems.
The system is suitable for a college, hostel, residential society, small company or local
service office.

2. Overall Description
2.1 Product Perspective
OCMS is a new, self-contained, three-tier web application: a browser front end, a Python
back end that holds the business logic, and a relational database. It has no dependency on
any existing system, and every user reaches it through a web browser.
2.2 Product Functions (Summary)
Register, log in, reset a forgotten password and manage a profile.
Submit complaints with category, priority, description and attachments, and receive a
unique complaint number.
Track status, view history and the full activity timeline of each complaint.
Admin: review, assign, reprioritise, respond to and close complaints; manage users,
staff and categories.
Staff: see assigned complaints, update progress and add resolution notes.
Email notifications, feedback and rating after closure, reports with CSV/PDF export.

2.4 Operating Environment
Client: any modern browser (Chrome, Edge, Firefox) on desktop, tablet or phone.
Server: Windows or Linux with Python 3.10 or later.

Email: SMTP server (for example Gmail SMTP) for notifications.
2.5 Design and Implementation Constraints
The back end must be written in Python using a web framework (Flask or Django).
Passwords must be stored only as salted hashes.
Uploaded files are limited to 5 MB each and to JPG, PNG or PDF types.
The project must be completed within the academic semester using open-source tools
only.
2.6 Assumptions and Dependencies
Users have internet or intranet access and a valid email address.
An SMTP account is available for sending notifications.
The organisation supplies the list of complaint categories and staff.
A single server instance is enough for the expected load of up to a few hundred users.

5. Non-Functional Requirements
ID Attribute Requirement
NFR-1 Security Passwords are hashed with salt; sessions expire
after 30 minutes of inactivity; all forms carry CSRF
tokens.
NFR-2 Security All database access uses the ORM or
parameterised queries to prevent SQL injection;
output is escaped to prevent XSS.
NFR-3 Security Uploaded files are checked for type and size,
renamed with a random name and stored outside
the public web root.
NFR-4 Security A user can see only their own complaints; staff can
see only assigned complaints; admin pages reject
other roles with a 403 error.
NFR-5 Performance Common pages load within 3 seconds and list
pages show 10 to 20 rows per page (pagination)
with up to 50 concurrent users.
NFR-6 Usability A new user shall be able to register and file a
complaint in under 3 minutes without training.
NFR-7 Reliability Complaint data is saved in a database transaction,
so a failure never leaves half-saved records; a daily
database backup is taken.
NFR-8 Availability The system should be available at least 95% of the
time during working hours.
NFR-9 Scalability The design is modular so new modules, such as
SMS, can be added, and the database can later
move to a larger server.
NFR-10 Maintainability Code follows PEP 8, is split into modules (models,
views, services, templates), carries docstrings and
has configuration in environment variables.
NFR-11 Portability The system runs on Windows and Linux with the
same code.
NFR-12 Compatibility The interface works on the current versions of
Chrome, Edge and Firefox and on mobile browsers.

6.2 Complaint Workflow
1. The user registers or logs in.
2. The user submits a complaint and receives a complaint number.
3. The system stores it with status Submitted and notifies the admin.
4. The admin reviews it, sets the priority and assigns a staff member.
5. Staff work on it and update the status, adding notes the user can read.
6. The user tracks progress and can comment at any time.
7. Staff mark it Resolved and the user is asked for a rating and feedback.
8. The complaint becomes Closed when the user confirms or after 7 days.

6.3 Complaint Status Lifecycle
A complaint normally runs left to right from Submitted to Closed. Withdrawn is only
possible before assignment, Rejected needs a written reason, and Reopened returns the
complaint to staff. Overdue is a flag set by the scheduler when the SLA deadline passes,
not a separate status.
7. Database Design
OCMS uses a normalised MySQL schema (third normal form). PK = primary key, FK =
foreign key. The original proposal's separate Admin table is merged into a single Users
table with a role column, which removes duplicate login logic.
